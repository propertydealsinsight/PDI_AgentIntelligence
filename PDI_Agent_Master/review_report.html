PDI_AgentIntelligence · PDI_Agent_Master review

Agent Master matching — how big is the problem, and what do we do about it

Companion to AGENT_MASTER_REVIEW_BRIEF.md. All figures below are measured against production PDI_PortalsData on 2026-07-13 via the read-only account, or sampled/extrapolated from it — each number below says which.

Headline: the matching engine has been live 12+ months without a visible incident because most of what it does is right, and the failure mode (wrong branch, right brand) mostly shows up as double-counted stats rather than a customer-facing error. But it is not a rare edge case: roughly 1 in 3 cross-portal matches sits in a branch group where the same brand name attached to more than one address on the other portal, and about 1 in 10 of all matches is a wrong branch pairing we can already prove is wrong with data we already have.

The fix is layered on purpose: a chunk of this is fixable today with no new rule and no risk to the "obviously right" majority; a chunk needs a new address-matching rule that has to be designed and validated first, precisely because a low-evidence match isn't always a wrong one — small, genuinely quiet branches look the same in the data as a bad match. Rushing that part is how we'd trade one class of error for another.

1 · The whole picture

63,617 rows in pdi_agent_master today

Just over a third are cross-portal matches (a Rightmove branch paired with a Zoopla branch). The rest are single-portal rows — and that split is not itself an error. Rightmove and Zoopla will always have real coverage differences: measured independently of the master table, Rightmove carries 49,364 distinct (agent, branch-address) pairs against Zoopla's 30,490 — Rightmove genuinely has ~62% more branch listings to begin with, so RM-only rows outnumbering ZL-only rows is expected, not a sign the matcher missed them. The thing worth calling an error is specifically §2–4 below: branches that were matched, to the wrong counterpart.

One nuance the single/cross split doesn't capture at all: active vs. inactive. Some single-portal (and matched) rows are agents who simply aren't trading any more — the master has no concept of this today, which is a separate, real gap (see D1 below), not the D7 matching-quality problem this report is mostly about.

6 · D1 — is a stable master id actually safe to introduce?

Checked, not assumed: nothing joins on agent_master_id today

Direction agreed with Moiz: id should become a permanent key — assigned once, never reassigned on rebuild, with an active/inactive status added so a decommissioned agent gets flagged rather than silently vanishing or being reissued to someone else. The open question was impact: does anything outside this table rely on the id's current (unstable) values, such that changing how it behaves would require touching other systems?

Searched every repo this account has access to for the literal column name. Result: agent_master_id appears in exactly one place outside PDI_PortalsData itself — PDI_Agent_Performance, where it is written into the performance table purely as a traceability column (agent.id copied in at upsert time). It is not the join key anywhere: the read side (FETCH_AGENTS_QUERY) selects p.id only to iterate the current snapshot within a single run, and every actual lookup — the performance table's own unique key, and the ranking API's joins in PropertyDataDBAPIs — goes through (agent_name, agent_address), ZL-first. Nothing in MarketIntelligenceFeed, the RM/ZL merge procedures, or any other repo references the column at all.

Practical consequence: the stored agent_master_id in the performance table already changes every week under the current unstable scheme (the pipeline re-fetches from whatever snapshot exists at run time) — nobody currently treats it as durable, so nothing breaks by making it durable. This is a low-impact, additive change: make the existing id column stable and add the active/inactive flag, rather than introducing a parallel column or requiring any downstream migration. Worth a final grep pass closer to implementation time in case something references it indirectly (e.g. a saved report or ad-hoc script outside these repos), but nothing found here argues against just doing it.

7 · Rollout

Now / next / later

Roll out now

Low risk, no new design decision

  • D2 loop-1 bug — fixed in repo (procedure/p_generate_agent_master.sql, commit 1f04fb1): the RM exclusion join compared against the master's ZL columns instead of RM, so it was a silent no-op. One-line fix, isolated commit after a baseline commit of the unmodified procedure. Not yet deployed — needs a CREATE OR REPLACE PROCEDURE against production before the next scheduled run picks it up.
  • Retrofit the ~2,500 provable-wrong rows — for every branch-group, keep the sibling with the strongest shared-listing evidence, demote/delete the rest. Uses the existing diagnostic query; no new matching rule required.
  • Commit the diagnostic queries into the repo as permanent tooling (done — queries/ folder) so this check can be re-run on demand, not just during this review.
Next — needs design + validation

The ~3,700 ambiguous rows, and the rule itself

  • Design the address-correspondence rule (postcode sector match, or address-string similarity) and the minimum-evidence threshold — pick both from the real distribution, not a guess.
  • Run a full outcode-by-outcode census (chunked like the procedure's own loop, to respect read-only execution-time caps) to replace today's 33/40-branch sample with exact figures before trusting the threshold.
  • Build the rule into Loop 1 and re-validate against the ~3,700 ambiguous rows specifically — this is where a wrong threshold would misclassify a genuinely small, quiet branch as a bad match.
  • Build the validate-then-swap gate (row counts, duplicate-group share, matched-vs-single-portal split) before the fixed procedure ever runs unattended.
  • D1 — direction agreed (permanent id + active/inactive status, see §6) and impact-checked as low-risk; still needs the actual implementation: how the rebuild's create-fresh-table-and-rename pattern carries ids forward instead of reassigning them, and the active/inactive definition itself (e.g. no listing activity in N months on either portal).
Separate track

Structural decisions (brief §2, D3/D4)

  • D3 — duplicate rows overall; should shrink sharply once D7 is fixed, but a unique-constraint decision is still separate.
  • D4 — RM-first vs. ZL-first canonical name/address; needs sign-off from Agent Performance, MarketIntelligenceFeed, and the ranking API (brief §D5) before changing.
  • These don't block the D7 rollout above, but they do need their own decision before the master rebuild is considered "done."
Methodology: figures in §1 and the 17.3%/4.5%/35.9% group-scope numbers are exact, from full-table aggregate queries against PDI_PortalsData.pdi_agent_master (63,617 rows — cheap to scan in full). The 49,364/30,490 RM-vs-ZL branch counts in §1 are exact independent counts direct from property_details/property_details_zoopla (grouped on the indexed agent_name, agent_address pair), not from the master table. The confidence-tier split in §2 and the bucket chart in §4 are extrapolated from capped, per-branch shared-listing-evidence queries against a random sample (33 duplicate-group branches, 40 clean branches) — the full evidence-count computation across all 23,282 matched branches in one query timed out against the production read-only cap and was abandoned rather than pushed harder, per the standing rule for this database (see [[pdi-portals-readonly-db]]); a proper census needs to be chunked the same way the procedure itself chunks by outcode. The §6 impact check is a literal-string repo grep for agent_master_id across every repo this account can reach (PDI_AgentIntelligence, PropertyDataDBAPIs, PDI4Institutions, PDI_InsightJavaRepo2025, PDICommercialProspects, PDI_ZooplaAdapter) — a real but not exhaustive check; it can't see code this account doesn't have access to.
